# Task Report: H17c — Lock-Free SPSC Streaming Music Ring Buffer

## 1. Problem Statement & Findings
1. **Non-Atomic Data Race on `sMusicRingCount`:**
   - Previously, `sMusicRingCount` was modified concurrently: `+= chunk` on the producer side (`UpdateMusicStream()` / main thread) and `--` on the consumer side (`AudioCallback` / `AudioThread`).
   - On both x86_64 and MIPS Allegrex architectures, non-atomic read-modify-write operations on shared integers without locks create race conditions leading to corrupted count tracking and buffer desynchronization.
2. **Producer/Consumer Boundary Blurring:**
   - The audio callback was attempting to run `UpdateMusicStream()` directly when free space was detected, executing blocking file I/O inside real-time audio threads.

## 2. Changes Implemented

### 2.1 Single-Producer Single-Consumer (SPSC) Ring Buffer Architecture
- Eliminated `sMusicRingCount` entirely.
- Strict ownership invariants:
  - `sMusicRingHead` is written **solely** by the Producer (`UpdateMusicStream()`), and read by the Consumer.
  - `sMusicRingTail` is written **solely** by the Consumer (`AudioCallback` / `AudioThread`), and read by the Producer.
  - Number of readable samples available to consumer:
    $$\text{count} = (\text{head} - \text{tail} + N) \pmod N$$
  - Number of writable slots available to producer:
    $$\text{freeSpace} = (\text{tail} - \text{head} - 1 + N) \pmod N$$
  - Usable capacity: $N - 1 = 32767$ samples (where $N = \text{MUSIC\_RING\_BUF\_SAMPLES} = 32768$).
- Memory barrier enforcement:
  - Added `__sync_synchronize()` before publishing new `head` values after writing PCM data to `sMusicRingBuf`.
  - Added `__sync_synchronize()` before publishing new `tail` values after reading PCM data.
- Removed blocking file I/O calls (`UpdateMusicStream()`) from audio callback threads.
- Added telemetry getters:
  - `AudioEngine::GetMusicRingSampleCount()`
  - `AudioEngine::GetMusicRingCapacity()`
